I · O problema que nenhuma ferramenta resolve

MIXR ajuda — mas só se usado direito

  • O framework já vem com uma dinâmica de eventos e classes-base pensadas para resolver esse acoplamento sem que cada par de modelos precise se conhecer diretamente.
  • Mas isso só funciona se o framework for usado do jeito que foi desenhado para ser usado.
  • Exige entender as abstrações, o vocabulário, o uso idiomático — um MIXR mal utilizado não entrega nada disso de graça.

I · O problema que nenhuma ferramenta resolve

A proficiência em modelagem — física, comportamento, interações do domínio — é uma barreira que nenhuma ferramenta, processo ou framework vai amenizar. Ela é intrínseca ao que estamos simulando.

O que dá para fazer: garantir que tudo o que NÃO é essa dificuldade intrínseca pare de atrapalhar.

II · A proposta

Uma reestruturação para devolver produtividade e escala

A expectativa não é remover a dificuldade de modelar — é recuperar produtividade e capacidade de escalar, atacando todo atrito evitável.

  • Ferramentas usadas do jeito certo — MIXR, BehaviorTree.CPP, Groot
  • Um repositório só, não vários espalhados
  • Esteira de CI forte — testes em camadas, Makefile claro
  • Contrato forte de modelo — docs/, CHANGELOG.md
  • Ferramentas de assistência — painel ao vivo, manual, editor visual
  • Documentação com apoio de IA + filosofia poc-first
  • Ambiente padronizado — VSCode, clangd
  • Roadmap — integração com o asa-engine

II · A proposta

Ferramentas usadas do jeito que foram desenhadas

  • MIXR e BehaviorTree.CPP não são bibliotecas genéricas — são frameworks com opiniões fortes sobre como o código deveria se organizar.
  • A aposta é usá-los como foram desenhados, em vez de reconstruir por fora o que eles já resolvem por dentro — é isso que faz a dinâmica de eventos do MIXR funcionar a nosso favor.
  • Groot entra como a ferramenta de edição e monitoramento das árvores de comportamento — visual, não só texto.
  • Extensão VSCode para .edl: realce de sintaxe e validação de verdade — o mesmo parser do framework, antes de tentar rodar. clangd no lugar do IntelliSense padrão para C++.

II · A proposta

Um contrato forte para todo modelo

  • Todo modelo que entra no repositório carrega a mesma espinha dorsal: documentação de arquitetura em docs/.
  • E um CHANGELOG.md que registra o que mudou e quando — por data de commit, nunca por data da mensagem.
Por quê

Mensagem de commit se engana. Data de commit não. Isso é gestão de conhecimento de verdade: o conhecimento não fica só na cabeça de quem escreveu — fica registrado de um jeito que sobrevive à saída da pessoa.

II · A proposta

Documentação com apoio de IA + a filosofia poc-first

  • Não é terceirizar a explicação para uma IA e aceitar o que sai.
  • É usar IA como alavanca para produzir e manter atualizada uma documentação que, historicamente, é a primeira coisa a envelhecer mal em qualquer projeto de engenharia.
  • Em vez de desenhar a arquitetura ideal no papel antes de escrever qualquer linha, a aposta é começar simples, com uma prova de conceito pequena.

poc-first, na prática

poc pequena→ vira contrato→ vira exemplo de como fazer→ próximo modelo copia e adapta

Um caminho já percorrido para copiar e adaptar — não um documento de intenções.

III · Onde estamos

Código é, por natureza, uma forma difícil de guardar conhecimento — mesmo em uma linguagem tão legível quanto Python. Reescrever um modelo antigo é a oportunidade de recuperar esse conhecimento, com documentação e testes junto.

E esse é o melhor momento possível para isso — com IA tornando muito mais viável ler, entender e reescrever código antigo.

IV · O convite

Comece pelo TOUR.md

  • Um roteiro guiado, pensado para não exigir conhecimento prévio do repositório — exatamente o problema que ele existe para resolver.
  • Leva você a subir o ambiente, rodar um cenário de verdade, ver a simulação no Tacview, explorar o painel de controle, abrir o manual interativo.
  • Segunda trilha, para quem quiser ir mais fundo: o editor visual de cenários, o Groot, a decisão em Python, o ambiente de treino de RL.

IV · O convite

Estresse o metaprojeto

  • O convite não é só "leia a documentação" — é rode, quebre, proponha melhorias, reporte erros.
  • Amigável e plug-and-play não significa livre de erros — significa que encontrar e reportar esses erros já é parte esperada e valiosa do processo.
  • Em docs/books: dois livros escritos com apoio de IA, um sobre o MIXR e outro sobre o BehaviorTree.CPP — material de capacitação para quem está entrando agora.
Por quê

Um sistema assim só amadurece com gente de verdade tentando usá-lo.
