Metaprojeto de simulação · MIXR + BehaviorTree.CPP

poc-mixr

Um padrão de engenharia para experimentar modelos de simulação — não um framework novo, e sim um jeito de organizar experimentos sobre o MIXR e o BehaviorTree.CPP em que cada variação muda um eixo só, deixando tudo o mais idêntico e comparável.

A · Contexto

Uma PoC para novos modelos — não para o MIXR em si

  • MIXR é dependência binária. Consumido como pacote Conan (mixr/1.0.5); não é objeto de desenvolvimento deste repositório.
  • BehaviorTree.CPP v3.5.6, também binário — uma .a estática de 35 MB, 447 símbolos globais.
  • O fork é headless. Não publica mixr_graphics/glut/ instruments/ighost — não existe janela GLUT neste repositório.
  • Toda visualização passa por telemetria de verdade: Tacview Real-Time Telemetry, via shared/xtacview.
Regra de consulta

contexts/src/ guarda o fonte completo do MIXR e do BT.CPP para consulta — mas é git-ignored, não vem num clone limpo. Em caso de dúvida entre a doc destilada e o fonte, o pacote Conan é quem vale: é ele que está linkado.

A · Contexto

Um eixo por vez

Cada subprojeto muda exatamente uma coisa. Comparar duas pastas mostra, byte a byte, o que de fato varia — make compare-single-multi não é força de expressão, é um alvo de Makefile que faz diff de verdade.

Onde decide

single-thread / multi-thread

Mesmo cenário, mesmo modelo. Só muda a thread e a fase do frame em que o agente decide.

Em que linguagem decide

python-flight / onnx-policy

Mesma árvore de comportamento (ou nenhuma). Muda o que ocupa a folha de ação: script ou rede.

Que cenário roda

built-in_mixr_1

Aplicação idêntica à single-thread, byte a byte. Só o EDL — o player — muda.

B · Princípios de padronização

Estrutura vem do EDL, comportamento vem do C++

Players, sensores, taxas, threads — tudo isso é dado, declarado num arquivo .edl (a linguagem de definição de cenário do MIXR). Reconfigurar o cenário nunca recompila nada.

Parâmetros configuráveis são slots: BEGIN_SLOTTABLE/ON_SLOT no C++, casados por nome contra o EDL. A fábrica resolve por nome, encadeando local → xtacview → simulation → models → recorder → base — a primeira que reconhece o nome vence.

falcon1.edl (trecho) 
agent: ( FlightAgentTC
   state: ( FlightState )
   behavior: ( BtBehavior
      treeFile: "flight_tree.xml"
      patrolMasterSeed: 20260903 )
)

B · Princípios de padronização

README · Funcionalidade 04

A mesma física em todas as seis variações

Sob qualquer agente — SimAgent, FlightAgentTC, Python ou ONNX — quem voa é o JSBSim, já integrado ao MIXR: 6 graus de liberdade, aerodinâmica tabelada, motores com transiente de partida real. A decisão muda; o avião que ela pilota é sempre o mesmo.

  • O modelo é um c310 bimotor a pistão (engIO470D, maxrpm 2625) — calibrado especificamente para ele: taxa de subida, raio de manobra, folga anti-CFIT.
  • JSBSimModel::reset() roda RunIC() mas não FGTrim — a aeronave começa destrimada, com um transiente energético real nos primeiros segundos.
  • O Autopilot nativo fecha malha de rumo e altitude, mas não de velocidade — sem manete fixo a aeronave perde energia e estola.
MEDIDO — em t≈1s empuxo ~0 e 1,16 RPM; em t≈7s, ~400 lbf e 2700 RPM

B · Princípios de padronização

Um único executável roda todas as pocs

Nenhuma poc tem binário próprio. ./app é o runner: app -scenario <chave> ou app -f <arquivo>. Cada pasta em src/poc/ é só configs/ + data/ + README.md — nunca código.

  • Antes: cada poc carregava ~1.500 linhas de aplicação duplicadas, sustentadas por uma guarda de teste — e uma correção teve de ser copiada à mão, uma a uma, para cinco pastas.
  • Hoje: a duplicação está dissolvida por construção.
MEDIDO — dump frame= byte-idêntico ao binário antigo (600 frames, -threads 2)

O modelo é um plugin, construído antes do host

Armadilha

BT.CPP é estática (35 MB, 447 símbolos T); sem -Wl,--exclude-libs,ALL o plugin reexportaria tudo isso. Com a flag, o .so de 11 MB exporta um símbolo.

B · Princípios de padronização

Três projetos Meson, ordem obrigatória

Toolchain: Conan 2.x → Meson/Ninja → Makefile (orquestra). O modelo não é mais um alvo do host — é um plugin construído numa etapa anterior.

configure→ sdk→ models→ build→ install (sync-plugins)→ test
  • build/models são decoplados de propósito — compilar o host nunca presume onde os modelos guardam artefatos, e vice-versa.
  • make models deposita em plugins/ (nunca em dist/ diretamente); só make install sincroniza os dois.
  • dlopen() só em tempo de execução — por isso nada disso é necessário para compilar um binário, só para rodar um.

B · Princípios de padronização

O padrão shared/x<nome>

Atravessa o dlopen — precisa de uma cópia só no processo

xboardxlogxtrack xrlbridgexinferxpyembed

Fica só no host — static_library()

xtacviewxclockxjoystick xmsgxplugin (header-only)

Um plugin que linkasse as estáticas ganharia uma cópia privada delas — xlog::setLoggingEnabled(false) nunca alcançaria o lado do modelo. As seis shared_library() existem exatamente onde host e plugin precisam compartilhar estado mutável em runtime através da fronteira do dlopen.

C · Organização do repositório

plugins/ ≠ dist/ ≠ build/, de propósito

models/*/install-host→ plugins/ (.so + data/, flat)→ make install (sync-plugins)→ dist/ (o que roda)

Compilar um modelo nunca precisou saber onde o host guarda os artefatos dele — dlopen() só acontece em tempo de execução. Um .so de terceiro entra em plugins/ pelo mesmo caminho e fica indistinguível de um compilado por este repositório a partir desse ponto.

O intruso: joystick físico, emitido por DIS nativo

  • Joystick físico — shared/xjoystick lê /dev/input/js* cru (ioctl, sem SDL/evdev); um Logitech Extreme 3D mapeia 4 eixos (roll/pitch/pedal/manete) via UsbJoystick declarado no EDL, canal por canal.
  • Sem hardware, o Autopilot assume sozinho — hasRealJoystick() confere se /dev/js<N> existe de verdade antes de tocar em qualquer coisa; plugar o joystick no meio da execução troca para manual sem reiniciar nada.
  • single-thread/multi-thread não têm mais bandit1: local — recebem esse player só pela rede, via dead reckoning a cada PDU.
Armadilha

Comentários em .edl têm de ser ASCII puro. Um único acento ("só") num comentário, sem relação com o resto do arquivo, derrubou o parser inteiro com "syntax error" — sem dizer o motivo.

Por que a condição não migra

ContactDetected depende de uma histerese que envelhece com o dt do frame — e a fronteira de shared/xpyembed é 28 floats entram, 3 saem, sem dt. Sem essa histerese os dois ramos de evasão/apoio alternariam para sempre a cada vez que a pista piscasse.

README · Funcionalidade 12

onnx-policy — o mesmo eixo, levado ao extremo

Uma folha só, ( OnnxPolicy ), carrega um MLP 28→64→64→3 (6.211 parâmetros, 25 KB) e infere dentro do frame — sem Python no processo.

Treinada por clonagem de comportamento: não é RL, é o caminho mais curto entre uma regra que se sabe escrever (uma barreira geométrica) e uma rede que voa. A árvore some porque a política treinada é o mapa observação→ação inteiro — inclusive o "quando evadir".

O árbitro nativo continua acima

( AltitudeSafetyBehavior vote: 90 ) vence ( BtBehavior vote: 50 ) sempre que necessário. Na fixture de terreno, 32/32 linhas do dump saem bt=SAFETY — trocar de política nunca revalida a segurança de voo.

MEDIDO — 50,1 µs/inferência (0,25% de um frame de 20 ms) convergência em 160 s sim, erro médio 0,27° de rumo

Tacview — reaproveitando o gravador nativo do MIXR

TacticalOutput é um recorder::OutputHandler de verdade, encaixado na cadeia nativa do slot dataRecorder: da Station — não há stream ACMI montada à mão em nenhum main.cpp.

Handshake simples: XtraLib.Stream.0\nTacview.RealTimeTelemetry.0\n..., bind em 0.0.0.0; cada subprojeto tem sua própria porta, então dá para abrir várias sessões ao mesmo tempo (File → Real-Time Telemetry).

Armadilha

dataLogTime é slot do Player e nasce zero — sem dataLogTime: ( Seconds 0.1 ) o player nunca emite dado nenhum e some do Tacview, em silêncio. E PlayerState.pos/.angles chegam em ECEF/geocêntrico — é preciso converter com convertEcef2Geod() antes de plotar.

README · Funcionalidade 09

Log e telemetria — configuração, não recompilação

LOG(NIVEL) << ...; (shared/xlog) escreve em console, arquivo e num buffer circular em memória ao mesmo tempo — a mesma cópia é lida tanto pelo host quanto pelo modelo, aberto por dlopen.

shared/xmsg vai além: um ( MsgFeed ) no EDL escolhe o quê sai da simulação e quando — condições de mudança/limiar/taxa (MsgChanged, MsgThreshold, MsgRate) — sem tocar em C++.

Vazamento de memória — pelos contadores que o MIXR já mantém

  • mixr::base::MetaObject já conta count/mc/tc por classe, nativamente — nada precisou ser instrumentado no modelo para ter esse dado.
  • O painel Memória lê xplugin::pluginMetaObjects() — cobre automaticamente qualquer plugin carregado, inclusive um de terceiro, sem um nome de classe escrito à mão no dashboard.
  • discoverPlayers() varre mixr::models::Player — a classe BASE —, não uma lista fixa: um míssil liberado em runtime aparece sozinho.

contador não é atômico → corrigido com racyCounter, não com lock

F · Decisão por aprendizado de máquina

src/rl — treinar dentro do mesmo processo

Um módulo pybind11 mantém a Station viva no mesmo processo Python — sem round-trip de rede por passo. falcon1 vira ( RLBridgeBehavior vote: 50 ) dentro do mesmo UbfArbiter que já tinha ( AltitudeSafetyBehavior vote: 90 ).

Uma política ruim do agente de RL não derruba o avião no terreno — o árbitro nativo sobrepõe sem precisar de código novo.

Armadilha de ordem de import

import mixr_gym tem de vir antes de numpy/gymnasium no processo — senão a primeira chamada a reset() segfaulta dentro de libstdc++ (estouro de TLS estático do glibc com muitas extensões C já carregadas).

F · Decisão por aprendizado de máquina

Do treino ao runtime, sem Python em produção

src/rl (treino, Gymnasium)→ export_onnx.py→ policy.onnx→ shared/xinfer (produção)

A ordem dos 28 campos de observação vem de uma X-macro só (ObservationFields.hpp), expandida contra domain::WorldView no modelo e contra xrlbridge::Observation na ponte — um nome que divergir entre as duas structs não compila. Não há lista escrita à mão em Python em lugar nenhum.

G · Filosofia de engenharia

"Medido, não hipotético." Toda decisão de design tem uma armadilha documentada e um número medido — nunca uma redescoberta.

dumps byte-idênticos, 1/2/4 threads 42 µs/decisão (Python) 50 µs/inferência (ONNX) RSS plano após SO_SNDTIMEO

G · Filosofia de engenharia

Convenções que substituem disciplina por guarda

  • Português em docs, comentários e mensagens de console; inglês em identificadores, slots e nomes de fábrica — originais do MIXR.
  • Sem prefixo numérico. O repositório já foi uma progressão numerada (01-flying-aircraft … 12-jsbsim-ubf) — essas pastas não existem mais, e o prefixo não é mais convenção.
  • Guardas automatizadas, não lembretes: check_host_opaco.sh, check_modelo_estrutura.sh, check_falcons_estrutura.sh travam invariantes estruturais sem depender de ninguém lembrar deles.
